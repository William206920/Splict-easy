## 二、产品核心目标

手机优先、填表式记账，支持平均与按实际金额分摊混合记账，最后统一结算。普通用户无需学习编程或记账语法。

主要流程：打开网页 → 添加人员 → 填写消费名称、付款人和总额 → 选择分摊方式 → 填写参与者或个人金额 → 添加消费 → 重复记账 → 统一结算 → 查看每人应收应付和转账 → 复制结算单。

AI 扩展流程：用户主动使用 CLI 的 --ai → 查看即将外发的账单和目标服务 → 确认发送 → 获取结构化解析 → 校验并处理歧义 → 查看逐笔解析预览 → 确认后调用同一个 MoonBit 核心结算。

## 四、技术架构

- shared/：金额、账单模型、校验、分摊、结算、文本及 JSON 解析、渲染。
- web/：MoonBit JavaScript 后端；原生 HTML/CSS；少量 DOM、存储和复制 FFI。
- cli/：Native 参数、文件 IO、可选 AI API；调用 shared，不重复业务算法。
- fixtures/、examples/：固定测试与示例；.github/：CI 与部署。

所有业务计算在 shared；shared 不依赖 DOM、文件系统或网络。不得手写业务 JavaScript；JS 构建产物必须由 MoonBit 生成。无大型前端框架、外部 CDN、数据库。默认数据保留在设备上，只有显式 AI 模式允许主动发送账单到用户选择的模型服务。

## 六、数据模型及金额约束

金额全部是 Int64 整数分：300 元=30000 分，300.50 元=30050 分，0.29 元=29 分；禁止浮点计算金额。JSON 读写也必须保持 Int64 精度，不能经普通 JS Number 中转。

```text
Share: person: String, amount_cents: Int64
Payment:
  payer: String
  amount_cents: Int64
  split_mode: Equal | Exact
  participants: Array[String]
  shares: Array[Share]
  description: String
  date: String
Ledger: people: Array[String], payments: Array[Payment], ambiguous: Array[String]
Transfer: from: String, to: String, amount_cents: Int64
```

equal 使用 participants，shares 为空；exact 使用 shares，participants 为空。人员必须在总名单中且不重复。消费总额大于零；个人份额非负，允许零；exact 合计必须等于总额。所有累计检查溢出。ambiguous 非空时阻止继续处理。具体类型语法使用实际工具链验证。

## 七、平均分摊

A 分由 n 人分：base=A/n，rem=A%n。参与者按 Ledger.people 的声明顺序排列，前 n-rem 人承担 base，最后 rem 人承担 base+1。100 元三人分别为 33.33、33.33、33.34 元。必须守恒，允许付款人不参与。

## 八、按实际金额分摊

逐人输入承担金额，零表示不承担。五人奶茶份额示例：小明 12、小红 15、小刚 18、小美 14、小李 16 元，合计 75 元。合计不等于付款总额时禁止添加，并给出中文错误；不得自动补齐或修改金额。

## 九、统一结算算法

净额=实际已付-应承担；正数应收，负数应付。每轮重新选择最大余额债权人与欠款绝对值最大债务人，转账双方绝对值较小值，更新直至归零。同额按人员声明顺序。

描述为“尽量减少转账次数”，不承诺全局最少笔数。必须保证净额总和零、每笔转账大于零、无自转账、最终全部归零、同输入同输出、不溢出。

## 十一、手机网页

人员区：添加、改名、删除；拒绝空名与重名；改名同步更新全部引用；有关联消费时删除必须提示并要求先处理，不能静默丢数据。

消费表单：名称、付款人、实付总额、分摊方式、明细及添加按钮。平均模式可勾选并预览份额，付款人可不参与；实际金额逐人填，实时显示合计与差额，合计不符禁止添加。

消费列表：显示名称、付款人、金额、模式、参与人数，支持编辑和删除。修改后清除或标记旧结算失效。

结算区：总消费、每人已付/应付/净额、转账和复制按钮。最大宽度约 640px，输入框字号至少 16px。用户文本统一安全转义。默认离线，不上传账单。

## 十四、Native CLI

```bash
spliteasy check -f bills.txt
spliteasy split -f bills.txt
spliteasy split -d ledger.json
spliteasy split -d ledger.json --json
spliteasy split -f bills.txt -o out.md
spliteasy split -f free.txt --ai
```

- -f 与 -d 互斥；check 只解析校验，不生成转账。
- 默认 Markdown；--json 输出 JSON；-o 写文件。
- 错误到 stderr，失败非零退出；参数解析可测试。
- 非 AI 模式不联网，也不读取模型配置。
- --ai 用于自然语言 -f 输入；-d 已是结构化账单，不再调用模型。
- 交互确认和预览使用独立于最终机器输出的通道，不能污染 --json 或 -o 的结果。
- 未取得交互确认或用户取消时不自动外发、不结算；不得以静默默认同意绕过确认。

## 十五、AI 自然语言解析：阶段 8 必交付

示例输入：

> 我们五个人吃饭，小明付了 200 元，大家平摊。后来小红买了五杯奶茶，总共 75 元，小明 12 元、小红 15 元、小刚 18 元、小美 14 元、小李 16 元。

需要识别人员、消费名称、付款人、总额、模式、参与者及个人金额，并转换为 Ledger。AI 不生成最终余额和转账；不得信任模型给出的计算结果。

仅在 --ai 时读取 MOONBIT_BASE_URL、MOONBIT_API_KEY、MOONBIT_MODEL，使用兼容 Chat Completions API。密钥不进入网页、仓库、日志、截图或演示材料。

必备流程：

1. 读取自然语言文件，展示将发送的内容和目标服务，明确会离开设备，取得发送确认。
2. 使用用户配置的服务调用模型；真实远程调用需要可用配置和密钥，不能用模拟结果冒充。
3. 使用严格结构和无损金额解析读取模型响应，再由 MoonBit 执行完整 Ledger 校验。
4. 缺人名、付款人、金额、参与范围，出现矛盾或指代歧义时提示补充，不猜测；ambiguous 非空时阻断。
5. 展示可读逐笔预览：名单、付款人、总额、分摊模式、各人份额、缺失字段和问题。结构校验不能保证模型理解正确，因此必须保留人工核对。
6. 用户确认后才结算；取消则不生成结算结果。不自动覆盖原账单或草稿。用户修订或重新解析后重新校验、预览、确认。
7. 请求失败、超时、认证失败、无效 JSON、未知人员、份额不符和溢出都有中文错误，不输出伪成功结果。

阶段 8 验收证据：

- 真实兼容服务解析五人混合案例；经人工确认后由核心得到黄金 B 的结果。
- 一个缺信息/歧义案例，展示阻断与补充流程。
- 一个无效响应或请求失败案例，展示错误处理。
- 模拟测试独立覆盖成功、歧义、非法金额/结构、服务错误、发送取消、解析后取消及无确认输入。
- 演示材料标清真实模型与模拟场景；记录服务和模型名称、日期及实际结果，隐藏密钥和私人账单。

若真实模型配置尚不可用，可先完成实现和模拟测试，但本项保留“真实演示待验收”；不得宣称 AI 参赛交付已完成。若面临延期，先删 P2，并压缩可选界面优化；不得悄悄把本项改回可选。

## 十六、输出格式

HTML：消费、模式、余额、转账；应收绿，应付红，并有文字含义；所有用户文本转义。

JSON：余额和转账顺序稳定，全部金额整数分；保留既定报表 schema。账单导入 schema 与报表输出 schema 明确区分。

10. 验收标准。
11. Git commit 建议及实际同步状态。
