## 三、产品目标与范围

开发一个普通人可安装、可双击启动的 Windows 桌面 AA 分账应用。

1. 启动 SplitEasy.exe，创建或打开本地账单。
2. 添加人员，输入消费名称、付款人、总额和可选日期。
3. 选择平均分摊或按实际金额分摊。
4. 勾选参与者或逐人填金额，添加消费，可继续编辑和删除。
5. 点击统一结算，查看个人汇总和转账清单。
6. 复制结算单，保存账单或导出结果。

核心特点保持不变：平均与不平均消费可以混合记录，最后统一结算。晚餐五人平摊、奶茶按各自价格填写，系统自动汇总抵扣。

AI 流程：主动打开 AI 解析入口 → 输入自然语言 → 确认目标服务和外发文本 → 模型解析 → MoonBit 校验 → 逐笔预览 → 再确认 → 核心结算。配套 CLI 保留 --ai 入口。

本期平台：Windows 10/11 x64。最低具体系统版本、DPI 和运行库依赖以实际构建测试为准。不承诺未测试的 ARM、macOS、Linux GUI 或手机支持。Linux 可用于纯核心测试。

本期单币种人民币、精确到分，每笔一个付款人。多人付款可拆成多笔。退款、跨币种、实时协作、支付接口及云账户不纳入必交付。

程序界面不使用 HTML、DOM、WebView、Electron、Tauri 或浏览器页面；可选的文档网页不构成应用界面。

## 五、技术架构与原生路线

MoonBit Native 作为主程序与主要业务实现，通过官方 C FFI 调用 Windows Win32 Unicode 控件和系统 API。

| 层 | 职责 | 边界 |
| --- | --- | --- |
| shared | 金额、Ledger、校验、分摊、结算、文本/JSON 与报表 | 纯 MoonBit，不依赖 GUI、网络或文件系统 |
| app | 账单编辑状态、输入验证、事件分发、结果失效、AI 预览 | MoonBit 实现，调用 shared |
| platform/win32 | 窗口、控件、事件、剪贴板、文件对话框、系统能力 | 少量 C ABI 桥接，不实现分账计算 |
| storage | 本地账单和草稿流程 | schema 与校验复用 shared |
| cli | 配套命令行、文件与参数 | 不重复算法 |
| ai | 请求、模型配置、严格解码、两次确认流程 | GUI 与 CLI 共用服务和校验逻辑 |

采用原生 EDIT、BUTTON、COMBOBOX、列表和对话框等系统控件，中文文本走 Unicode。由 MoonBit 驱动业务状态与控制流，C 仅提供平台适配。

不得通过“大部分业务改写成 C/C++”规避 MoonBit 为主要求。不得在未验证时承诺 MoonBit 可以直接生成 DLL；本路线由 MoonBit 可执行入口链接 C stub，不依赖导出共享库。

第一阶段必须验证 Windows 编译、打开窗口、中文文本与按钮事件能回到 MoonBit。若工具链或 FFI 路线实测受阻，记录问题并修复或提出最小替代；不能偷偷换成 HTML 界面。

金额、名单、尾差、净额、转账规则完全沿用第七至第十节。

## 七、金额与数据模型

所有核心金额使用 Int64 整数分，禁止浮点计算：

| 用户输入元 | 核心整数分 |
| ---: | ---: |
| 300 | 30000 |
| 300.50 | 30050 |
| 0.29 | 29 |

金额解析支持非负十进制整数或一至两位小数，例如 `12`、`12.3`、`12.30`。不接受负号、指数、千位分隔符、多余小数或自动四舍五入。UI 如去除首尾空白，应在输入层统一处理并明确测试。

核心接受范围不超过 Int64 可表示的非负整数分。每笔、总额、个人累计、份额合计及相关运算均须在运算前检查溢出。

概念模型如下，具体 MoonBit 语法必须编译验证：

```text
Share:
  person: String
  amount_cents: Int64

Payment:
  payer: String
  amount_cents: Int64
  split_mode: Equal | Exact
  participants: Array[String]
  shares: Array[Share]
  description: String
  date: String

Ledger:
  people: Array[String]
  payments: Array[Payment]
  ambiguous: Array[String]

Transfer:
  from: String
  to: String
  amount_cents: Int64
```

约束：

- equal 只使用 participants，shares 必须为空；至少有一名参与者。
- exact 只使用 shares，participants 必须为空，防止字段冲突。
- payer、participants 和 shares 中的人必须在 Ledger.people 中。
- 名单、参与者和同笔 shares 的人员不能重复；空白姓名不能通过。
- 人员姓名本期不支持空格；文本保留标记及分隔符的限制需在各入口一致说明和校验。
- 消费总额必须大于零；个人份额可以为零，不能为负。
- exact 份额合计必须等于消费总额，不猜测、不自动补差。
- exact 未列出的名单人员视为该笔承担零，不得把差额自动分给他们。
- description 在普通表单必填；高级文本缺省规则必须有说明。
- date 可为空；提供日期时采用 `YYYY-MM-DD` 并校验有效日期，不补猜历史日期。
- ambiguous 非空时可展示待补充问题，但不能作为有效账单结算。
- 尚无消费时可保存草稿，界面提示先添加消费，不生成误导性的付款要求。

## 八、平均与实际金额分摊

### 平均分摊

A 分由 n 人承担：

```text
base = A / n
rem = A % n
```

参与者按 **Ledger.people 的声明顺序**排列，不按勾选时间、participants 数组传入顺序或字母排序改变尾差。

前 `n-rem` 位承担 base 分，最后 rem 位承担 base+1 分。rem 为零时每人都是 base。

100 元三人分别承担 33.33、33.33、33.34 元。1 分三人分别承担 0、0、1 分。付款人可以不参与。

### 按实际金额分摊

五人奶茶示例：

| 人员 | 承担金额（元） |
| --- | ---: |
| 小明 | 12.00 |
| 小红 | 15.00 |
| 小刚 | 18.00 |
| 小美 | 14.00 |
| 小李 | 16.00 |
| 合计 | 75.00 |

总实付为 75 元时才能添加。界面显示已分配金额与差额；不符时提示例如“还差 2.00 元未分配”或“已多分配 2.00 元”。不能自动更改任何人的金额。

未参与人员可以明确填零。空输入可作为表单编辑中的未完成状态，不能在未告知用户时当作有效金额提交。

## 九、混合账单与统一结算

```text
个人净额 = 所有消费中的实际已付合计 - 应承担合计
```

正数表示应收，负数表示应付。展示时区分“应承担消费”与“结算需转出”，避免混淆。

采用确定性贪心算法：

1. 每轮选择当前余额最大的债权人。
2. 选择欠款绝对值最大的债务人。
3. 转账双方余额绝对值的较小值。
4. 更新双方余额，重新选择，直至全部归零。
5. 同额时按 Ledger.people 声明顺序选择。

对外描述为“尽量减少转账次数”，不保证数学意义上的全局最少笔数。

必须保证金额守恒、净额之和为零、每笔转账正数、无自转账、回放后全部归零、同输入同输出及无整数溢出。无人需要转账时明确显示“无需转账”。

## 十一、Windows 桌面界面

主界面提供人员管理、消费编辑、消费列表与结算结果，可用分区或标签页组织，不能把所有字段塞进固定尺寸窗口。

人员：添加、改名、删除；拒绝空名重名。改名更新全部引用；有关联消费时删除必须先处理引用，不静默丢数据。

消费：名称、付款人、总额、可选日期、方式与明细。平均模式勾选人员并预览；实际金额显示合计与差额。切换模式只能提交当前模式字段，不能自动假设用户已同意金额转换。

列表：名称、金额、付款人、方式、日期及承担人数，支持编辑与删除。编辑可取消；保存后替换原记录。人员或消费变化后旧结算失效，不能继续复制旧结果。

结算：总额、已付、应承担、净额、转账与复制；无人需要转账时明确提示。状态不能只靠红绿颜色。复制失败提供可选文本，不虚报成功。

桌面要求：窗口可调整尺寸，内容可滚动；100%/125%/150%/200% DPI 下不遮挡关键操作；使用系统字体，中文输入法可用；标签、Tab 顺序与键盘操作明确。

原网页的 640px 最大宽度、手机字号、横竖屏与浏览器适配不再作为主验收条件。

## 十二、本地文件、草稿与 JSON

本地能力由平台桥接和 MoonBit 控制层提供：打开/保存对话框、UTF-8 文件 IO、剪贴板、用户数据目录和错误状态。不得使用 localStorage 或 DOM。

- 正式账单文件带 schema_version，完整保存名单、消费与顺序。
- 自动草稿放在当前用户可写的数据目录，例如 LocalAppData 下的 SplitEasy 子目录，不写程序安装目录。
- 保存采用先写临时文件再替换等安全方式；失败不损坏旧文件。
- 恢复草稿须校验版本与内容；损坏、不兼容和权限错误中文提示，不自动覆盖仍可恢复内容。
- 未保存更改在关闭窗口或打开其他账单前提示保存、放弃或取消。
- 导入先解析、校验、预览，确认替换后才改变当前账单。
- 草稿/导出不包含 API Key；本期密钥默认只在会话内使用或从显式 AI 配置读取，不以明文持久保存。

金额 JSON 约定保持：canonical JSON 的 amount_cents 等字段为十进制整数分数字记号，使用能直接读取原始整数的 MoonBit 路径，无浮点中转。账单文件与报表文件的 schema 区分清楚。

测试 Int64 上限、超过 JS 安全整数范围的无损往返、非法结构、未知版本和金额溢出。第三方解析器是否无损由其能力决定，文档说明这一点。

## 十三、离线、安装与运行边界

正式交付：Windows x64 便携 ZIP、SplitEasy.exe 和可安装/卸载的发行包。用户运行不需要安装 MoonBit、Python、浏览器或启动本地服务器。

程序启动、记账、保存、结算、复制与导出必须可以断网运行。必要运行库应打包或在安装器中明确处理；不能缺少依赖却宣称开箱即用。

仅用户主动启用的 AI 解析联网；安装程序和普通计算不偷偷发送账单。自动更新不属于本期必交付。

验收区分 Windows CI 编译、Windows 自动窗口检查和用户桌面实测。无交互的 CI 不能替代输入法、显示缩放和实际安装操作的人工验收。

## 十四、高级文本记账

基本语法：

```text
人：小明 小红 小刚 小美
小明 300 晚餐
小红 120 加菜
小刚 40 饮料 !小红
```

精确分摊：

```text
人：小明 小红 小刚 小美 小李
小红 75 奶茶 =小明:12 小红:15 小刚:18 小美:14 小李:16
```

指定与排除多个人：

```text
小明 60 午餐 @小明 小刚
小红 90 门票 !小红 小美
```

规则：

- 人员声明在消费之前，姓名用空白分隔，不支持姓名内部空格。
- 一行一笔；前两个字段为付款人和金额，其后是消费说明及可选分摊标记。
- 默认全员平均；`@` 指定、`!` 排除、`=` 指定实际金额份额。
- 同笔只能使用一种分摊标记，拒绝混用、未知或重复人员、空参与集合及不合法金额。
- 说明可包含空格；保留标记不能在说明中无转义地冒充普通文本。具体限制写入语法说明并统一测试。
- 精确金额合计必须匹配总额。
- 保留原始行号，空行不能使后续报错行号偏移。
- 支持 Windows 换行和 UTF-8 BOM，错误为带原始行号的中文说明。
- 日期等未在文本中提供的可选字段不猜测补齐。

文本只是高级入口；普通表单不要求用户学习这些符号。

## 十五、Native CLI

至少支持：

```bash
spliteasy check -f bills.txt
spliteasy split -f bills.txt
spliteasy split -d ledger.json
spliteasy split -d ledger.json --json
spliteasy split -f bills.txt -o out.md
spliteasy split -f free.txt --ai
```

规则：

- `-f` 文本输入与 `-d` JSON 输入互斥，并且必须提供一个有效输入。
- `check` 只解析和校验，不生成转账。
- 默认 Markdown，`--json` 输出报表 JSON，`-o` 写文件。
- stdout 保留给最终输出，错误、交互提示与预览走 stderr 或独立终端通道。
- 非零退出码区分失败；文档记录实际采用的退出码。
- 文件不存在、权限不足、非法内容、未知参数、缺少参数值均需清楚报错。
- 失败时不写半份报表，不把错误当作成功输出。
- 非 AI 模式不联网，不读取模型配置，也不因缺少密钥而失败。
- `--ai` 只用于 `split -f` 自然语言输入；与 `-d` 或 `check` 组合时明确拒绝并说明。
- 参数解析与业务执行流程可测试；Native IO 与 HTTP 采用当前工具链实际可用的接口，依赖及最小平台桥接如实说明。
- 为 Windows 用户给出经验证的命令或明确列出待验证步骤，不把 Linux 结果当作 Windows 原生构建结果。

## 十六、AI 自然语言解析：阶段 8 必交付

目标是把自然语言转换为待核对的结构化账单，再由 shared 校验和结算。应用内提供 AI 输入与预览对话框，CLI 保留 --ai。两端复用请求、解析与校验规则；GUI 确认通过对话框，CLI 通过明确交互。

示例：

> 我们是小明、小红、小刚、小美、小李。小明付了 200 元晚餐，五人平摊。后来小红付了 75 元奶茶，小明 12 元、小红 15 元、小刚 18 元、小美 14 元、小李 16 元。

识别名单、消费说明、付款人、总额、方式、参与者和实际金额。模型输出中的最终余额或转账不能作为核心结果采用。

CLI 仅在 `--ai` 时读取以下环境变量；GUI 仅在主动打开 AI 功能时允许填写或读取对应配置：

```text
MOONBIT_BASE_URL
MOONBIT_API_KEY
MOONBIT_MODEL
```

使用兼容的 Chat Completions API。文档说明 BASE_URL 与路径拼接规则，密钥不写入源码、仓库、普通账单、日志、截图或演示材料。

必须实现：

1. **发送前确认。** 展示将发送的账单文本、目标服务与模型，说明数据会离开设备。未确认或取消时不发送。
2. **实际请求。** 使用用户配置的可用服务，处理超时、认证、网络与服务错误。GUI 请求异步执行，不能阻塞窗口；提供取消和进行中状态。
3. **严格解析。** 明确 JSON schema、金额单位与必填字段，采用无损金额路径；响应结构不能直接当作可信账单。
4. **MoonBit 校验。** 检查人员、模式、金额、合计、溢出和 ambiguous。
5. **歧义阻断。** 缺姓名、付款人、金额或参与范围，或存在矛盾指代时要求补充，不猜测。
6. **解析后预览。** 展示逐笔付款人、总额、方式和个人份额。即使结构校验通过，也需要人工核对语义。
7. **第二次确认。** 只有确认当前预览，才能调用结算；取消不生成结果，不自动覆盖原文件或草稿。
8. **重新解析。** 修改或补充后重新校验、预览、确认；重新外发仍需对应确认。
9. **无交互输入。** 不能静默默认同意；未取得确认时返回明确状态。
10. **输出隔离。** 确认与预览不能污染最终 `--json` 或 `-o` 文件。

模型提示词要求对未知信息返回 ambiguous，而不是编造。但不能宣称提示词或结构校验能够发现所有理解错误，因此第二次确认必须保留。

阶段 8 的证据：

- 真实服务解析五人混合案例，核对后得到黄金 B。
- 至少一个缺信息或歧义案例，展示阻断、补充及再确认。
- 至少一个失败场景，展示中文错误而非伪成功。
- 模拟测试覆盖成功、歧义、非法结构/金额、无效 JSON、服务错误、两处取消和无确认输入。
- 实际演示记录服务、模型、日期和结果，标明哪些场景真实调用、哪些使用模拟。

实现与模拟测试完成但真实配置不可用时，状态只能是“真实模型演示待验收”。不得把 AI 改回可选交付，不得用模拟响应冒充真实服务。

## 十七、统一报表与输出
